# Назойливый куратор / Annoying (OmFEST CTF Challenge)

CTF-таск на демонстрацию двухэтапной цепочки атак: **Cookie Stealing через Stored XSS** (Фаза 1) и **Cross-Site Request Forgery (CSRF)** (Фаза 2).

## Описание
В ретро-корпоративном мессенджере ЗАО «ГлавСпецСвязь» (стилизация под Windows 2000 / корпоративный интранет 2000-х):
- **Фаза 1 (Stored XSS & Cookie Stealing):**
  - При регистрации пользователя подозрительный бот **«Начальник»** шлет приветственное сообщение (`WELCOME_MESSAGE`).
  - Каждые 15 секунд Начальник под своей учетной записью заглядывает в диалог через headless-браузер **Lightpanda**.
  - Сессионные куки не имеют флага `HttpOnly`, а сообщения рендерятся без санитизации HTML (`safe`).
  - На сервере включён **жёстко зашитый чёрный список HTML-тегов** (`BLOCKED_HTML_TAGS` в `app.py`: `script`, `img`, `svg`, `iframe`, `object`, `embed`, ...), который вырезает наиболее распространённые XSS-пейлоады.
  - Список **регистрозависимый**, поэтому пейлоад со смешанным регистром тега (`<ScRiPt>`) проходит фильтр — это и есть задуманный обход.
  - Эксплуатируя Stored XSS, игрок перехватывает сессионный токен Начальника.

- **Фаза 2 (CSRF через подсистему «Служебные записки»):**
  - Авторизовавшись под учетной записью Начальника, игрок обнаруживает диалог с Генеральным директором, однако в переписке флага нет: директор сообщает, что секретные коды перенесены в защищенный реестр, а выдача допуска осуществляется через новый раздел мессенджера — **«Служебные записки и согласования»** (`/memos`).
  - В данном разделе Начальник может направить служебную записку со ссылкой на аудит/материалы. Генеральный директор лично переходит по указанной ссылке со своего терминала под своей активной сессией.
  - На странице также представлена форма согласования (`/memos/approve`), не защищенная CSRF-токеном и доступная только Директору.
  - Игроку не требуется настраивать свою машину или внешний сервер: достаточно перенаправить запрос Директора на внутренний адрес этого сервиса (`http://web:5000/memos/approve` или `/memos/approve`). При переходе бота Директора выполняется CSRF-атака: Директор утверждает допуск и направляет секретный флаг Начальнику в личные сообщения.

## Переменные окружения
- `FLAG`: Текст флага (по умолчанию: `OmFEST{c00k13_st34l1ng_xss_l1k3_4_b0ss}`).
- `WELCOME_MESSAGE`: Приветственное сообщение Начальника новому сотруднику.
- `PORT`: Порт веб-приложения (по умолчанию: `5000`).
- `CHECK_INTERVAL`: Интервал проверки диалогов и служебных записок ботом в секундах (по умолчанию: `15`).

## Развертывание (Docker / CTFd)
Для локального запуска или тестирования через docker-compose:

```bash
docker compose up -d --build
```

Либо классическим запуском одного контейнера:

```bash
docker build -t annoying .
docker run -d --name annoying -p 5000:5000 annoying
```

### Деплой в CTFd (плагин `instances`)
1. Архив для загрузки в CTFd: `annoying.tar.gz` (содержит `docker-compose.yaml`, `Dockerfile`, `supervisord.conf`, `entrypoint.sh` и исходные файлы `src/`).
2. Тип челленджа: `instance`.
3. Контейнерный порт (Container Port): `5000`.
4. Сервис принимает переменные окружения `FLAG` и `PORT` от плагина CTFd и автоматически запускает веб-приложение, Lightpanda и бота через supervisord.

## Проверка решаемости (важно!)

Эмпирически (запуск реального контейнера и перебор ~40 векторов) установлено,
что **Lightpanda исполняет JavaScript только двумя способами**:

- тег `<script>` — работает в любом регистре и с пробелами/атрибутами,
  включая `<script src="data:text/javascript,...">`;
- атрибут `onload` на теге `<body>` (HTML-парсер сливает атрибут с body
  документа, и обработчик срабатывает на событии `load`).

Не исполняются обработчики на других элементах (`onerror`, `onfocus`,
`ontoggle`, `onstart`, `onbegin`, `onplay`, ...), `javascript:`-URL,
`<iframe srcdoc=...>`, `<object>`, `<embed>`, `<svg>`/`<math>`-контексты.

Следствия для фильтра:

- Любой фильтр, который **полностью** нейтрализует `<script>` **и**
  `<body onload=...>`, делает Фазу 1 нерешаемой, а значит и весь таск —
  нерешаемым: другого JS-синка в Lightpanda нет.
- Поэтому чёрный список намеренно **регистрозависимый**: он режет обычные
  lowercase-пейлоады (`<script>`, `<body onload=...>`, `<img ...>`), но
  пропускает `<ScRiPt>` / `<BoDy onload=...>`.

Проверка после включения фильтра выполняется скриптом `solve.py` (он использует
смешанный регистр тега) — см. раздел «Эксплуатация».
